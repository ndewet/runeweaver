# Performance comparison for PRs #117–#121

The comparison uses main at `e8f30dc` and the complete PR stack at `c926fda`.
The reported scan regressions do not persist with an isolated scan benchmark.
The benchmark harness needs to change before the PR stack is evaluated again.

Both builds use Rust 1.98.0, one code generation unit, thin LTO, and the locked
benchmark dependencies. Source paths are mapped to the same virtual directory.
The Windows host has an AMD Ryzen 7 9700X. The Linux comparison uses the same
host through Docker, with the Linux Rust 1.98.0 toolchain.

Each scan processes at least 512 KiB. Measurements use 200 samples, one second
of warmup, and three seconds of measurement. Each comparison pins execution
to one CPU. The repeated comparisons alternate base-first and candidate-first
order. Builds finish before the final measurements start.

## Assembly

The Linux scan functions for the three cases flagged by CI have these counts:

| Scan case | Main instructions | PR stack instructions |
| --- | ---: | ---: |
| Rust-like | 3,694 | 3,694 |
| Lisp-like | 1,052 | 1,052 |
| Mode actions | 779 | 779 |

Rust-like scanning is in a separate `try_fold` function. The other two scans
inline into Criterion's iteration function. Symbol normalization and comparison
of the referenced byte tables show identical instructions and table contents.
Windows Rust-like scanning also has identical instructions: 3,767 in each build.

Other cases demonstrate the limits of instruction counts. Linux punctuation
scanning has 305 non-padding instructions on main and 300 on the PR stack.
Nevertheless, the original PR executable scans more slowly. Linked function
addresses, block order, and padding differ. Fewer instructions do not guarantee
a faster executable.

## Repeated measurements

The original harness gives these changes against main in three Linux pairs:

| Scan case | Original harness | Isolated scan function |
| --- | ---: | ---: |
| JSON | +7.59% to +10.38% | −10.02% to −6.16% |
| Keywords | +6.25% to +7.81% | −2.11% to +1.64% |
| Punctuation | +14.77% to +18.49% | +0.53% to +1.52% |

These are ranges of paired mean changes, not confidence intervals. Both
revisions receive the same `#[inline(never)]` annotation on the complete scan
function. Inputs, token counting, error handling, and sampling settings stay
the same. One call processes the complete input, so call overhead is small.

The result supports a harness-layout explanation for these large changes.
It does not establish identical performance in every consumer executable.
The original Windows comparison has no scan regression above 5% in three pairs.
Measurements that overlap build or validation work are excluded from conclusions.
A quiet same-executable control changes by −1.01% for JSON and +0.24% for
punctuation. A control that overlaps validation shows a large false slowdown.

An experiment aligns generated byte tables to 64 bytes. This does not remove
the Linux slowdowns. That experiment is removed from the final change.

## Complete suite with the corrected harness

The final Linux comparison measures all 12 generation benchmarks and all 11
scan benchmarks. Criterion analyzes the saved samples against main at a 99%
confidence level. No benchmark fails the existing 5% regression gate.

| Scan case | Change against main |
| --- | ---: |
| Rust-like | −0.05% |
| Lisp-like | −3.80% |
| Mode actions | +1.76% |
| JSON | −11.07% |
| Keywords | −0.07% |
| Punctuation | +2.88% |

The JSON change has a 99% confidence interval from −11.73% to −10.35%.
The largest scan slowdown is punctuation at +2.88%. The largest generation
slowdown is mode actions at +4.10%. Small costs remain possible below the gate;
these results do not establish zero cost for every new API feature.

## Benchmark changes

The benchmark profile now specifies one code generation unit and thin LTO.
Local runs therefore use the same settings as CI. The complete scan function
does not inline into Criterion's timing loop.

CI measures each base executable immediately before its candidate executable.
A change above the 5% gate receives a second comparison in the opposite order.
Both complete 99% confidence intervals must pass the threshold in the same
direction. The displayed interval covers both intervals without pooling samples.

Merge the benchmark changes first, then rebase PRs #117–#121. Comparing the old
harness with the new harness would measure two changes at the same time.
No lexer implementation change remains from this investigation.

Validation includes workspace tests in debug and release, Clippy with warnings
denied, formatting, documentation with warnings denied, and benchmark builds.
Nine benchmark-gate tests pass. A real Criterion invocation also verifies the
reverse-order runner and saved-sample analysis.

Raw assembly, measurements, and diagnostic scripts are kept locally under
`target/performance-investigation/`. That directory is ignored by Git.
